# implementation direction

ring64 is a general-purpose x86 and x86-64 cpu for the browser. the direction includes real mode, 16/32-bit protected mode, virtual-8086 mode, compatibility mode and 64-bit mode, together with reset and actual guest-driven transitions. ring3 is the first consumer, including windows games of both widths; its current loader or runtime does not define ring64's final cpu scope.

this is a working coverage and dependency map. package names below describe proposed contracts, not a fixed architecture, schedule or instruction-completeness claim. keep the direction current as implementation and measurements change. specifications contain behavior and acceptance criteria; this index carries coverage and sequencing.

## existing contracts

- [initial execution](initial-execution/spec.md): the guest-byte to generated-wasm execution path, imported long-mode state, bounded discovery, exits, budgets and artifact ownership.
- [long-mode addressing](long-mode-addressing/spec.md): sib/rip-relative addresses and lea.
- [integer conditions](integer-conditions/spec.md): register logical operations, test and all sixteen flag-based jcc conditions.
- [integer memory](integer-memory/spec.md): memory operands for the existing arithmetic and logical operations.
- [stack and near control flow](stack-and-near-control-flow/spec.md): 64-bit push/pop, near call/ret and register-indirect transfers.

these contracts establish a usable execution core. they cover parts of several architectural areas; five implemented contracts do not close five of the thirteen areas below. source evidence identifies current coverage, not a fresh conformance or performance result.

## proposed packages and order

one package should carry a coherent behavior through decode, state, memory, lowering and verification. register/memory variants and operand widths belong together when they share that contract. implementation may use several small commits and checkpoints without opening a spec for each form.

the following groups give a preferred direction. independent branches can overlap; dependencies determine when a package can close.

`x87-state-and-execution` owns transcendental/special functions as well as arithmetic/conversions, including numerical edge behavior and status. the simd packages cover sse/sse2 families; each contract makes its feature-generation and numerical/state-control scope explicit. avx and wider extensions require explicit instruction, lane, enable-control and state-image coverage rather than an implicit inclusion or exclusion under the simd label.

these names are proposed boundaries. a spec may merge or split a group when the actual contract warrants it; no total spec count is a completion target. optional instruction extensions can add packages without redefining existing behavior.

## dependency rules

- **starting and closing are different.** an imported context can make a walker, numeric operation or descriptor path independently testable. that area is not complete until real guest control changes, feature enablement and downstream execution agree.
- **fault detection precedes full delivery.** integer, paging and segment owners can produce structured architectural outcomes before idt/iret is implemented. engine coverage failures and wasm traps must remain distinguishable.
- **backing and paging are different.** mutable ram/code, aliases and physical special-memory behavior can be implemented before guest page walks. page-table translation must use that backing policy rather than invent another one.
- **control effects stay with their consumers.** a paging contract includes the relevant cr3/control writes and invalidations; a numeric contract includes feature-enable effects. a giant completed system-instruction layer is not their prerequisite. system identity later checks the combined machine description.
- **architectural hidden state is not optimization metadata.** a gdt edit does not reload a segment. a context/map/code change must still invalidate or guard every generated assumption that depends on it, including pending compilation and middle entries.
- **multi-access behavior is instruction-specific.** repeated operations, enter, state images, event frames and vector operations do not inherit a universal all-or-nothing scalar transaction. retired instructions, completed suboperations and yield/poll work need separate meanings.
- **concurrency crosses every memory path.** locking only the lock-prefixed fallback is insufficient if ordinary accesses or other observers bypass its protocol. parallel execution must integrate with numeric-wide accesses, paging a/d updates, devices and executable bytes.

## completion and performance evidence

for each accepted contract, enumerate the supported families/forms/modes and their remaining gaps. a valid unimplemented operation is a coverage gap, not a guest invalid-opcode exception. feature absence, present-but-disabled behavior and engine failure have different outcomes.

verify independent expected results through decode, generated wasm and the complete host path. compare all relevant state and memory, defined/preserved flags, fault metadata, ordered external effects and repair/resume. exercise changed inputs and middle entries in retained code. save/restore and actual control transitions must preserve meaning across owners.

keep performance work alongside semantic growth. compare unchanged guest bytes and checked outputs before/after; characterize newly executable forms separately. measure translation and browser compilation/instantiation, first completion, early/later reuse, short resumes, code/cache memory, native entries, dispatch and relevant event latency. a reduced correctness scope is not a faster equivalent implementation.

memory access lowering, flags representation, region geometry, cross-artifact state transfer, indirect/return routing, cold execution and cache policy remain measured implementation choices. generic correct paths are valid baselines. promote an optimization when identical semantics and mixed workloads justify its compile, throughput, latency and resource costs; do not require a new architecture merely to add coverage.

## decisions to keep explicit

the broad cpu goal does not choose every vendor detail, feature generation, paging width, vector extension or concurrency policy in advance. the normal-mode direction above does not automatically include smm or virtualization extensions. decide the relevant scope before its contract is implemented, keep capability claims coherent, and record exclusions without presenting them as architectural invalidity.

in particular, preserve an explicit place for mode/reset transitions and legacy task/gate behavior, the numerical/state-control scope of vector extensions, physical/device and clock providers, browser capability fallbacks and the observer model for shared memory. ring3's first workloads inform priority and measurements while the cpu continues to support a wider general-purpose direction.
