# ring64 audit — 2026-11-07

Reviewed baseline: `3c89336e851cfaa4cbb261ab959a0eab39893af8`. Performance build: `2c9cd720c53971c4400e23ecc725e63d707fbf98`.

The implemented instruction families have substantial boundary and restart coverage. This audit found and fixed one initialization defect. Independent numeric, memory and execution-partition checks found no further actionable defect in the cases exercised. The largest remaining work is architectural: x87/MMX, guest protection and paging, event delivery, system state and mode transitions. Fifteen implemented specs do not complete the thirteen areas in [the scope map](../../specs/index.md).

## corrected defect

`createCpu` checked most required Core exports but omitted `core_multiply_high`, `core_divide` and `core_divide_failed`. A Core missing one of them could initialize successfully, then fail during instantiation of a generated module that imported that helper. That failure left the CPU unusable.

The factory now rejects each missing export before initialization. A regression test checks all three exports, initialization count and cleanup behavior. A separate reproduction removed exports from the real compiled Wasm module and confirmed the earlier late failure and the corrected early rejection. This changes validation of supplied compiler modules; the normal execution path is unchanged.

Two additional regression guards cover existing correct behavior:

- f64-to-f32 narrowing where the rounded bounded result is normal but underflow detection uses the result rounded with an unbounded exponent. Both signs, four rounding directions, underflow/precision masks, FTZ, old sticky status and suppressed destination writes are checked.
- retained source identity across all four split points of a five-byte instruction, execute-only remapping and reordered mappings; an identical-byte write through a writable alias still invalidates the translation immediately.

## repository and integration

Responsibilities remain separated: x86 state/decode and numeric semantics live in Rust; DBT owns discovery and Wasm generation; memory owns access policy; the host owns browser compilation, artifact lifetime and run coordination. The audit found no reason for a broad refactor or another cache/permission authority.

The toolchain is pinned to Rust `1.97.1`; npm and Cargo lockfiles are present. TypeScript uses strict checks, including unchecked indexed accesses and exact optional properties. `npm audit` reported zero registry advisories during this audit. A RustSec scan was not run.

Before this audit there was no GitHub Actions workflow or recorded Actions run. The added workflow installs Chromium and runs the complete check plus small Node/browser benchmark guards on pushes and pull requests. It uploads verification JSON. Those smoke runs check outputs and lifecycle, not performance thresholds on shared CI hardware.

The performance runner is now in the repository. Earlier research scripts under `/tmp` were insufficient as the only way to reproduce measurements. `npm run bench` and `npm run bench -- --browser` record build hashes, environment, phases, resources and checked results. A built checkout can be supplied with `--baseline`.

The inspected Ring3 dependency manifests and engine/SDK code paths contain no Ring64 integration. The repository does not provide a guest executable loader, operating-system ABI or game compatibility layer. Its tests enter prepared CPU contexts and memory. There is also no license file; distribution terms remain a separate repository decision.

The private memory map is useful backing infrastructure, not an x86 page walker. Imported legacy contexts exercise 16/32-bit forms, but do not demonstrate boot or guest mode transitions. Exporting a fault record does not demonstrate guest exception delivery. These distinctions explain why opcode progress alone understates the remaining work.

For application compatibility, x87 state/execution and then MMX/numeric state images are a useful next sequence: they add a missing numeric architecture and its shared-state rules. For general-purpose CPU depth, descriptor/protection state, guest paging/control writes and event delivery form the next dependency chain. Reset and mode transitions can then exercise that chain end to end. Feature identity and numeric enable controls must match implemented behavior along either path. These are priorities to specify and test, not a fixed count of future specs.

## current performance

Machine: Apple M4 Pro, macOS arm64. Node `22.16.0`; Chrome `157.0.8103.39`. Baseline and current used identical guest bytes and independently checked outputs. Both Core modules are 626,561 bytes with SHA-256 `2592681621d83b31b13cee79c92af6b17fe589854acbb09b9d3a864796ae88d7`. The rebuilt host hash changed for early export validation; Rust executable output did not change.

Each runtime ran eighteen kernels with eleven samples per side, alternating side order. The first sample records translation, compilation, instantiation and execution; the next three are early repeats and the last seven form the later window. Separate 31-sample controls cover noisy or small differences. The very short SIMD loop also has a ten-times-longer control to reduce browser timer quantization.

The table reports current-build later medians. Most kernels use 1,000,001 loop iterations; scalar kernels use a five-times multiplier, and budget-one uses 6,000 calls. Instruction counts include LOOP and any reset/setup instructions inside the guest loop. REP throughput counts completed bytes rather than instruction retirement.

The audit changes show no consistent slowdown in these cohorts. Initial later-window paired medians for packed add were +0.80% in Node and +1.15% in Chrome; the 31-sample controls reversed to -0.37% and -1.18%. The initial Chrome vector-load difference of -4.72% became effectively zero in the control. Budget-one controls remained noisy: paired medians were -0.23% in Node and +0.94% in Chrome, with individual pairs spanning roughly -41% to +34% across runtimes. No speedup or regression is attributed to early export validation. The unchanged Core hash provides additional evidence that instruction generation and numeric execution did not change, but does not replace timing checks.

For the bulk loops, each side compiles once on its first sample and reuses one artifact thereafter: one native entry per run, no dispatches and no later compilations. Generated modules occupy 683–914 bytes in these cases. Budget-one instead makes 6,000 native entries and 6,000 cache hits in a later sample. Cache hits therefore do not make frequent public run boundaries cheap.

The first current scalar-add completion took 10.267 ms in Node versus a later median of 7.189 ms; its browser-compilation phase took 2.460 ms. Other first phases can be much shorter because the same process has already compiled identical modules or related code. These samples do not establish an independent cold-process startup distribution. Current Core construction is recorded per kernel; it is outside the run timer.

The main measured costs are clear enough to guide profiling:

- Large native loops amortize host boundaries well. The scalar-add loop retires about 1.3–1.4 billion guest instructions/s here, counting LOOP. This is a simple fixed-operand microkernel, not a whole-CPU throughput estimate.
- Checked memory access is materially more expensive than the register loop. Scalar load reaches roughly 178–193 million guest instructions/s in its two-instruction loop; the mapping and permission work is part of the measured semantics.
- Exact numeric behavior is a separate cost class. Packed f32 add takes about 316–343 ms per million iterations, including MOVDQA reset and LOOP. This path preserves guest rounding/status and is not a native packed-add bandwidth measurement.
- One-instruction calls reach roughly 0.6 million instructions/s. State snapshots, coordination and boundary work dominate this particular workload. Source inspection confirms every native entry loads/publishes sixteen GPRs; XMM locals/publication are selected by use. This suggests a profiling target, not a proven optimization or a reason to change the state contract.

No speculative hot-path rewrite was made. More useful performance evidence would come from representative mixed guest programs, larger code working sets and controlled counterfactuals for state transfer, memory checks, numeric helpers and cache geometry. Native game performance, allocation peaks, multi-vCPU scalability and end-to-end Ring3 performance were not measured.
